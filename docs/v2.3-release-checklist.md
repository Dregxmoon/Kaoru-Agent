# Kaoru v2.3.0 release gate (draft)

Status: **not ready to tag or publish**. Until this gate is complete, freeze large features and focus on localization, installation, stability, and UX regressions. The working tree still identifies itself as v2.2.0; do not advertise a v2.3.0 installer yet.

## Localization contract

- English is the canonical source for new runtime UI strings. Spanish and Japanese must carry the same meaning, limitations, and security warnings.
- System language is used by default; unsupported languages fall back to English. A manual `system/en/es/ja` preference is validated in `set-config` and stored in `config.json` without replacing LLM, session, or workspace settings.
- Commands use canonical English names. Previous Spanish names remain aliases. `/memory` retains its existing history behavior; `/memory-graph` opens the explorer and `/memoria` remains an alias.
- Current localization is **partial**: chat controls, onboarding, settings, permission statuses, terminal toolbar, Memory Explorer, model picker, native confirmation dialogs, tray menu, and `/help` now use EN/ES/JA catalogs. A full inventory and human review of remaining generated text, errors, notifications, and overlay content are still required.
- Localized microphone controls do not make local speech recognition multilingual: the bundled Vosk resolver currently looks only for a Spanish model in `models/vosk-es/`. EN/JA recognition needs separate models, selection, packaging, and tests before it can be advertised.
- Do not release until an automated catalog parity check and a human UI pass in all three languages cover menus, buttons, settings, errors, permissions, onboarding, tooltips, and notifications. Avoid English fallback where a translation is required for safety or consent.

## Product documentation

- Reconcile the landing, guide, manual, root README, installation, model/API setup, permissions/privacy, troubleshooting, and CONTRIBUTING in EN/ES/JA. The Spanish technical manual and legal source remain the current maintained originals; do not label their translations complete before they exist.
- Verify command examples against `CommandRegistry.getNames()` and UI button labels against the shipped catalogs. Remove retired commands such as `/init` from active instructions.
- Regenerate the web with `node scripts/build-website.js`; run its check and website tests. Review links and all three language pages manually.

## Upgrade and clean-install matrix

Use disposable profiles and backups; **never** run factory reset or uninstall-data deletion on a real user profile.

| Scenario | Required evidence |
| --- | --- |
| v2.2.0 → v2.3.0 | Record config, model/provider selection (without revealing keys), memory counts, chat/terminal sessions, and workspace associations before and after update. Check that the new language field is added without losing unrelated fields. |
| Clean Windows install | Download installer, install, open, choose a model/API or local endpoint, open a workspace, complete a first read-only task. Check AppContainer status separately from the integrated PowerShell terminal. |
| Clean Linux install | Repeat with AppImage and/or deb; verify bundled native modules, voice, Live2D, PTY, and update behavior. |
| Clean macOS install | Repeat on Intel and Apple Silicon where available; document the platform-specific sandbox limitation. |
| No provider or invalid API key | Terminal still works; chat gives an actionable, localized error without claiming the key is stored or sent elsewhere. |
| Offline / provider outage | Model call and TTS fail clearly; local data and terminal remain intact. |
| Denied permission / invalid workspace | No unauthorized action; selected chat, memory, and config survive. |
| MCP failure / memory fallback / voice / Live2D / PTY | Show the correct degraded state, preserve data, and offer a recoverable next step. |

Run `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm test`, platform builds, packaged smoke checks, and CI on the tag. A skipped GUI test or mocked sandbox is **not** clean-install evidence. Publish one multilang build per platform (not three builds per language), then write release notes primarily in English with a Spanish summary and the known limitations.
